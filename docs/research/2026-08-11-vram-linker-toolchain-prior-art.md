# Prior Art for a Build-Time VRAM Linker

## 1. Classic linker technology

**GNU ld OVERLAY** ([sourceware.org docs](https://sourceware.org/binutils/docs/ld/Overlay-Description.html)) — exact semantics: all sections in an OVERLAY get the **same starting VMA** (run address); their **LMAs are laid out consecutively** starting at the overlay's load address. The linker auto-defines `__load_start_secname` / `__load_stop_secname` per member so runtime code can copy the right one in. After the overlay, the location counter advances by the **size of the largest member** — the exact "region is as big as its worst occupant" rule a state-overlay VRAM allocator needs. `NOCROSSREFS` makes cross-references between co-resident-impossible sections a **link error** — the direct ancestor of "object A may not reference object B's tiles because they never coexist."

**Over-budget reporting**: ld/ld65 both fail with byte-precise errors — ld: "section '.heap' will not fit in region 'RAM': overflowed by N bytes" ([example](https://github.com/ziglang/zig/issues/8563)); ld65: "Segment 'TILES' overflows memory area 'CHR' by 4096 bytes" ([nesdev thread](https://forums.nesdev.org/viewtopic.php?t=17765), [ld65 config docs](https://www.cc65.org/doc/ld65-5.html) — MEMORY areas with mandatory start/size + SEGMENTS assigned into them). ld also has `--print-memory-usage` (per-region used/total/%) — the minimal budget report format.

**ld's map file** gives: memory configuration, every input section's placement (address, size, source object), symbol addresses, and discarded sections; `--cref` adds a symbol cross-reference table. Good practitioner writeup: [Memfault, "Get the most out of the linker map file"](https://interrupt.memfault.com/blog/get-the-most-out-of-the-linker-map-file).

**Incremental-link stability**: MSVC `/INCREMENTAL` ([Microsoft docs](https://learn.microsoft.com/en-us/cpp/build/reference/incremental-link-incrementally?view=msvc-170)) is the main prior art. Mechanism: an `.ilk` database of previous placements; stability across small edits is achieved by **padding (slack) around functions/data** so they can grow in place, plus **jump thunks** when something must move. Key lesson: a shipping linker chose *explicit slack + prefer-previous-placement* over re-solving; and release builds re-link cleanly (non-incrementally) because the slack costs size. No mainstream linker tries to keep a *freshly solved* layout stable by tie-breaking toward the previous solution — that specific trick I found no source for.

## 2. Retro-dev toolchains

**SGDK** — rescomp does **not** assign VRAM ([rescomp.txt](https://github.com/Stephane-D/SGDK/blob/master/bin/rescomp.txt) compiles resources; you pass a tile index at `VDP_loadTileSet` time). VRAM management is **runtime**: the sprite engine allocator fragments under alloc/release churn — acknowledged in [SGDK issue #115 "Add VRAM defragmentation for the Sprite Engine"](https://github.com/Stephane-D/SGDK/issues/115), which shipped as `SPR_defragVRAM()` and `SPR_addSpriteSafe()` (retry-after-defrag). Community practice is "static tile allocation" (hand-picked base indexes) precisely to escape the allocator ([sprite_eng.h](https://github.com/Stephane-D/SGDK/blob/master/inc/sprite_eng.h)). This is the best cautionary tale for the runtime-allocation path.

**GBA** — grit converts graphics and can split maps into screenblocks (`-mLs`), but **charblock/screenblock assignment is manual** `#define`s; Tonc's guidance is conventions like "put map data in the unused tail screenblocks of a charblock" ([Tonc regbg](https://www.coranac.com/tonc/text/regbg.htm)). **No build-time VRAM allocation tool found.**

**SNES / libSFX** ([github.com/Optiroc/libSFX](https://github.com/optiroc/libsfx)) — has `Map.cfg` for memory-map configuration and superfamiconv for conversion, which "packs all of its data contiguously" and leaves VRAM layout correctness to the programmer ([MJP's writeup](https://therealmjp.github.io/posts/adventures-in-retro-development-snes-edition/)). **No VRAM budget solver found.**

**NeoGeo DATlib** — mostly moot: NeoGeo sprites render **directly from C-ROM**, so there is no sprite tile VRAM budget to allocate; DATlib's tools (buildchar etc.) arrange ROM-side tile data and handle the small fix layer ([DATlib 0.3 thread](https://www.yaronet.com/topics/189390-datlib-update-03), [fix layer wiki](https://wiki.neogeodev.org/index.php/Fix_layer)). Nothing transposes.

**Tanglewood** (github.com/BigEvilCorporation/TANGLEWOOD) — exact build/runtime split, verified from source:
- `bigevilframework/FRAMEWK/VRAMPOOL.ASM`: three fixed pools whose **boundaries are build-time equ math** (main tile pool, spare at 0xD000-0xE000, spare at 0xF400-0xFC00). Allocation itself is a **runtime bump arena**: `VRAM_PoolAlloc` walks pools smallest-first, returns `Start + Allocated`, no free ever (only `VRAM_ClearPools` wholesale reset per scene), and exhaustion is `RAISE_EXCEPTION error_out_of_vram` — a **runtime** error, not a build error.
- `bigevilframework/TANGLEWD/MEMMAP.ASM`: the rs-chains are the **68K RAM** map (`rsset 0x00FF0000`, 375 `rs.*` lines with `RS_ALIGN`). The `SharedVRAM_*` entries there are RAM **variables holding VRAM handles** (`rs.w 1` each) filled by runtime allocation. So Tanglewood's VRAM is build-time *pool extents*, runtime *addresses*.

**Dragon's Castle** ([variables.68k](https://github.com/sikthehedgehog/dragon/blob/master/src-68k/variables.68k)) — the strongest retro build-time example: VRAM tile addresses assigned at **assembly time via rsreset/rs.b chains** (`VramPlayer: rs.b 50`, `VramTileset: rs.b 178`, …), with per-stage graphics re-basing on a shared `StageVRAM` via repeated `rsset` (a hand-rolled overlay). Limits: purely sequential single-counter allocation, **no overflow check, no overlap check** across the manually coordinated per-stage rebases, no alignment/lifetime concept, no generated map.

**Local prior art**: `/home/volence/sonic_hacks/sonic_hack/VRAM_Layout.asm` — manual `equ` table with named pools (Zone Pool A/B, Core UI, Shared), sharing-by-comment ("shares with Sonic", "shares with Game_Over"), and `vram_bytes()`/`vram_art()` helper functions. Its own comments document the failure mode the linker fixes: `VRAM_PitcherPlant = $500 ; (moved from $3A0 — level art overflows to ~$449)` — a collision found at runtime and patched by hand.

## 3. Modern-engine analogies

**Texture atlas packing**: shipping tools use Shelf, Guillotine, **MaxRects** (best-short-side/best-area heuristics), and **Skyline** ([survey](https://ilovesprites.com/blog/texture-atlas-packing-algorithms), [skyline implementation writeup](https://jvernay.fr/en/blog/skyline-2d-packer/implementation/)). All are greedy heuristics run offline; nobody ships exact solvers. But this is 2-D machinery — VRAM tile ranges are 1-D and don't need it.

**The closest modern analogy is ML-compiler memory planning**, not atlasing: **TensorFlow Lite Micro's GreedyMemoryPlanner** ([memory_management.md](https://github.com/tensorflow/tflite-micro/blob/main/tensorflow/lite/micro/docs/memory_management.md)) packs buffers with **known lifetimes** into one arena: gather all allocations with size + lifetime, **sort descending by size, place each in the first gap where no lifetime-overlapping neighbor conflicts**, else append. TFLM also supports an **offline planner**: the plan is computed on the host and shipped as metadata (fixed offsets) — i.e., "solve offline, emit constants," exactly the proposed architecture, for RAM tensors instead of VRAM tiles. XLA's buffer assignment is the same idea at datacenter scale.

**Budget reports that work**: Chromium's [android-binary-size trybot](https://chromium.googlesource.com/chromium/src/+/master/docs/speed/binary_size/android_binary_size_trybot.md) + [SuperSize](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/tools/binary_size/libsupersize/README.md): every CL gets a **symbol-level size diff** (before/after/delta, attributed to source file), a hard threshold that fails review, and an explicit escape hatch (`Binary-Size:` justification footer) with human sheriff follow-up. [Bloaty](https://github.com/google/bloaty) markets the same "size diffs… perfect for CI" pattern. What makes these useful vs noise: **diff against baseline, attribute to owner, gate with an override that requires a written reason**.

**Bin-packing theory**: FFD's tight bound is **FFD ≤ 11/9·OPT + 6/9** (Dósa 2007, [paper](https://link.springer.com/chapter/10.1007/978-3-540-74450-4_1)) — but that's the multi-bin problem. Yours is single-strip placement with alignment, a few fixed anchors, and lifetime-interference (interval overlap) — TFLM's greedy is the proven-in-production algorithm for exactly that shape. At N < 100 items, if greedy ever fails while a solution exists, exhaustive/branch-and-bound search is milliseconds; there is no need for anything fancier. Alignment is handled by rounding candidate offsets up per-item (waste bounded by align−1 per item). Conclusion: **FFD-class + lifetime interference is adequate; optimality is a non-issue at this scale** — the only caveat is that greedy can report "doesn't fit" on a fittable instance, so back it with an exact fallback (cheap at this N) before declaring over-budget.

## 4. Determinism + verification

- **Determinism by canonical ordering**: TFLM's planner is deterministic because its input order is fixed (sort by size desc, stable tie-break on declaration order). General reproducible-builds practice is the same: sort inputs, never iterate hash maps into output. No linker I found documents a semantic tie-break rule beyond input order — so *document your sort key* (e.g., size desc, then module path, then name) and it's free.
- **Prefer-previous-assignment**: only real prior art is MSVC incremental linking's `.ilk` + padding (§1) — stability bought with slack, discarded for release. GNU gold had an `--incremental` mode along similar lines; it saw little adoption. **No source found** for a from-scratch solver that tie-breaks toward last build's layout — if you add "minimize diff vs previous map" as a secondary objective, that specific feature appears novel.
- **Layout diffs as review artifacts**: strong prior art — SuperSize trybot diffs on every CL, Bloaty CI diffs (§3). Nobody does it for a VRAM map, but the report design transposes verbatim.

## Synthesis

**(a) Closest existing mechanism to the full concept**: no single one. The closest *single* tool is **RGBDS's rgblink** ([rgblink(5)](https://rgbds.gbdev.io/docs/master/rgblink.5)): sections declare optional constraints (ORG/BANK/ALIGN) or "float," the linker deterministically finds addresses/banks, emits symbols, and errors when nothing fits — declare/solve/emit/error, but for ROM banks, with no lifetimes or sharing classes. The closest *algorithm+architecture* is **TFLM's offline memory planner** (lifetime-aware offline packing, emitted as fixed constants) — for RAM tensors, not VRAM, and with no human map or overlay semantics. ld's OVERLAY supplies the lifetime-sharing semantics but requires you to hand-write the layout.

**(b) Honest novelty claim**: every ingredient exists somewhere — declared regions + overflow-as-build-error (ld/ld65), auto placement of constraint-annotated floating sections (rgblink), same-address lifetime overlays with cross-reference errors (ld OVERLAY/NOCROSSREFS), lifetime-aware offline packing emitted as constants (TFLM), map files (every linker), size-diff review gates (SuperSize). **What nobody appears to have done**: apply any of this to *VRAM as a linked address space* — a build-time solver taking per-module declarations (size, alignment, lifetime/state, sharing class), packing per level/state, emitting tile constants, failing the build on overlap/over-budget, and generating a reviewable map. Genesis practice tops out at hand-maintained equ/rs chains (Dragon's Castle, sonic_hack) or runtime bump arenas with runtime OOM exceptions (Tanglewood) or runtime allocators with defrag APIs (SGDK). Also apparently novel: prefer-previous-layout tie-breaking in a fresh solve, and a VRAM layout diff as a review artifact. No source found contradicting either claim, but absence-of-evidence caveat applies — this is niche territory and closed-source commercial tools (e.g., 90s Sega/Nintendo internal pipelines) are unauditable.

**(c) Features worth stealing**:

1. **Byte-precise overflow errors naming region and overflow amount** ("segment X overflows region Y by N bytes/tiles") — ld65/ld error format. Instantly actionable, zero investigation needed.
2. **OVERLAY semantics for state-exclusive sharing**: co-located sections sized by max member, auto-emitted per-member start/size constants (à la `__load_start_*`), and a NOCROSSREFS-style build error when code references tiles of a non-co-resident state — GNU ld.
3. **Floating vs pinned declarations**: every allocation may optionally pin ORG/alignment/pool; unpinned ones float and the solver places them — rgblink's section model. Keeps hardware-fixed anchors (plane tables, hscroll, sprite table, character DMA windows) and solved regions in one uniform declaration language.
4. **TFLM's greedy plan algorithm**: sort descending by size, place in first lifetime-compatible gap, deterministic by construction; offline plan → emitted constants. Proven shape for exactly this problem class; add an exact-search fallback before declaring over-budget (trivial at N<100).
5. **`--print-memory-usage`-style per-pool summary** (used/free/%) in every build, plus full map with per-allocation provenance (which module declared it, which lifetime class) — ld map file practice via [Memfault's guide](https://interrupt.memfault.com/blog/get-the-most-out-of-the-linker-map-file).
6. **Layout diff as a review artifact + gated budget with justified override** — Chromium SuperSize trybot: diff vs baseline map on every branch, hard-fail thresholds, and an explicit "I meant to do this" footer that requires written justification. This is what makes a budget report signal instead of noise.
7. **Documented deterministic tie-breaking** (size desc → module path → name), and optionally **prefer-previous-assignment as a secondary objective** — lesson from MSVC /INCREMENTAL that placement stability has real value for diffability, minus its slack/thunk costs since you re-solve exactly.
8. **Build-time-sized runtime residual pools**: for genuinely dynamic art, steal Tanglewood's bump-arena-with-scene-reset (`VRAM_PoolAlloc`/`VRAM_ClearPools`), but let the linker allocate the *pool extents* so the static and dynamic worlds can't collide — the one thing Tanglewood didn't check at build time.
9. **Anti-pattern to design against**: SGDK issue #115 — runtime alloc/free of VRAM inevitably fragments and grows a defrag API; cite it as the justification for build-time-first with runtime arenas only as leaf pools.
10. **Cross-reference table analog** (`--cref`): emit which modules reference each VRAM range, so a human can answer "who breaks if this moves" from the map alone.
