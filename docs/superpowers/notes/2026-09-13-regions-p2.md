## 3. The fade, as measured

### 3.1 The rule, derived from source (and where the earlier note was wrong)

`PAL_FADE_FRAMES = 16` (`engine/effects/palette.emp:86`). `Effects_InstallPreset` arms on any non-zero
`ep_transition` (`tst.w`; the magnitude is never read). `Palette_LoadPal` then copies `ep_pal` into
`Pal_Target` and sets `Pal_Fade_Frames = 16`; `Palette_Compose` runs `Palette_DoFade` in the SAME tick
(the game loop calls it after the game state). `Palette_DoFade`:

```
        subq.b  #1, Pal_Fade_Frames
        bne   .step_frame          ; reached 0: snap the buffer to Pal_Target, copy Target -> Pal_Base
    .step_frame:
        btst    #0, Pal_Fade_Frames
        bne   .noskip              ; bit 0 SET (odd)  -> step
        rts                        ; bit 0 clear (even) -> nothing
```

So it **steps when the decremented count is ODD** — k = 1, 3, ..., 15 after the arm, eight steps, the first
on the arming tick itself — and snaps at k = 16. The inline comments ("step only on even frame parity",
"odd frame: nothing moved") say the opposite of the branch. Each step moves every 3-bit channel of the 48
words one unit toward the target. A channel d units away therefore arrives at **k = 2d - 1**.

**The earlier note ("16 frames, stepping each channel by 1 on even frames, ~0.27 s") was right about 16 and
the step size and wrong about the parity, and "0.27 s" is the bookkeeping window, not what the eye sees.**
The visible change lasts 2·max(d) - 1 frames: here d = 3, so the colours finish moving on the fifth frame
(~83 ms at 60 Hz). Only a palette seven units away would fade for 13 frames. Between k = 6 and k = 16
nothing visible moves, but each odd k still runs a full step (and pays for it, §5).

### 3.3 DEFECT — a fade in flight survives a crossing back, and finishes on the region you left. STOPPED.

Measured (witness finding R): crossed into the night row, turned back after 4 ticks (`Pal_Fade_Frames` 12),
re-entered row 1 at k = 11 after the arm; 24 ticks later the palette buffer AND CRAM are
`OJZ_Palette_Night` while the camera stands in row 1, whose palette is `OJZ_Palette`. Per tick
(row, `Pal_Fade_Frames`, channel distance from row 1's palette):

```
(9,15,1) (9,14,1) (9,13,2) (9,12,2) (9,11,3) (9,10,3) (9,9,3) (9,8,3) (9,7,3) (9,6,3)
(1,5,1)  (1,4,1)  (1,3,2)  (1,2,2)  (1,1,3)  (1,0,3)  (1,0,3) ...
```

Mechanism, from source: the crossing back installs `OJZ_Preset_Sec1` with `transition` 0, so
`Palette_LoadPal` takes its snap path (`palette.emp` `Palette_LoadPal`, the `lea Pal_Base` arm): it loads
`Pal_Base` and sets `Pal_Base_Dirty`, and **never touches `Pal_Fade_Frames`**. `Palette_Compose` copies the
base in (distance 0 for one instant), then — because `Pal_Fade_Frames` is still non-zero — runs
`Palette_DoFade`, which keeps stepping the buffer toward the OLD `Pal_Target` and, at 0, snaps the buffer
to it and copies it into `Pal_Base` too. The region's own palette is lost until the next install.

This is the "0 means keep" class TOTAL BINDING exists to delete, surviving in the palette channel: a state
one install armed outlives an install that did not ask for it. It needs a camera to re-cross an edge
within 16 frames of crossing it, which a steady run never does but a player turning round at an edge will.
**Not fixed: it is engine code and the design says step 5 touches nothing in the engine.** The obvious fix
is for `Palette_LoadPal`'s snap path to cancel a fade in flight (clear `Pal_Fade_Frames` and
`PAL_ACT_FADE`); it would carry the effects-gate ritual. `--strict-reversal` makes the witness assert the
region-exact answer and is red today. TAGGED for the controller.

## 4. The open questions riding with step 5

**Q3 / T6 — boot straight into a region with a different `ep_pal`.** Measured with the DEBUG boot mailbox
aimed at (4099, 256): at the init's exit — the first `GameState_OJZScroll_Update` entry, before any

with the recipe above (boot the DEBUG ROM with `Boot_At_X/Y = 4099/256`, `Boot_At_Flag = 1` written at

**The region-cache sentinel.**
- *Act reload:* there is no runtime act-reload path in the tree — `Game_State` is set to
  `GameState_OJZScroll_Init` only as `Game.entry`, i.e. at reset, and reset clears Work RAM (the cache and
  the palette state both start empty). Nothing to measure. Noted as a seam: a future reload path that does
  not reset `Palette_State` would carry an in-flight fade across it, the same class as §3.3.
- *A DEBUG warp inside the already-cached region:* measured both ways. **With the sentinel** (as shipped), the warp's
  `Parallax_CheckBoundary` rescans and re-installs the night preset: its fade arms toward the palette
  already showing (`Pal_Fade_Frames` 15, 14, 13, ...), no colour moves, and the eight step frames are paid
  anyway (~35,000 cycles each, §5). **Without it** (mutation M4, §6: the two sentinel lines deleted from
  `Debug_Warp_Consume`, never committed), nothing installs, nothing arms, no colour moves, and the witness
  still passes. So for IDENTITY the sentinel is not load-bearing on this warp: the cached rectangle
  already names the right region, and a warp to any other region misses the cache and rescans anyway.
  What it does buy is a re-install of the region's channels after something else changed them (the
  effects lab's chords install presets and raster programs live). Whether that is worth a redundant
  install on every warp (and, with a fading preset, a no-op fade) is a DEBUG-tooling call; TAGGED.

**Why the fade frames cost ~35,000.** `Palette_DoFade` rewrites 48 words, and `publish_compose_lines()`
then sets `PAL_ACT_VARIANT_STALE`, so `Palette_Compose` re-derives `Variant_Water_Deep` (bound in slot 0
by every OJZ preset; `palette.emp` records that derive at ~19,332 cycles) on every step frame. The same bit
is why a snap crossing with NO colour change (x = 2048) still pays ~20,000. And the steps run to k = 15
whether or not the colours have arrived: for this palette the last six step frames move nothing and
each still costs ~35,000. The design's old ARCH figure, "~3840 cycles during the transition window", was
off by about two orders of magnitude over the window; ARCH is corrected in this parcel.
