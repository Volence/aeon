# CHAR-6: the GLIDEFALL box restore keeps the centre (2026-09-13)

Parcel record for ledger row `CHAR-6` (`docs/lens-findings.jsonl`). Branch
`parcel/char6-lift`, based on `origin/master` `be50631a`. Sigil binary built at `1532b72f`.
Design inputs: `docs/superpowers/notes/2026-09-13-char46-repro-recipe.md` (§1, §6, §7).

## 1. What was wrong, re-grounded on this tree

`PState_EnterHooks` bound the `GlideFall` row to `PHook_AirEnter`, whose first instruction is
`jbsr PHook_EnsureStanding`. That hook compares the box word with `cd_stand_wh`, and on a
mismatch computes `(stand_h - current_h) >> 1` and does `sub.l d2, y_pos(a0)`. From the 21-high
ability box that is (39 - 21) >> 1 = 9 px up. The box grows from 21 to 39 with the feet planted,
so the head rises 18 px. Nothing checks the head's clearance first.

Decoded from the base ROM (`s4.debug.bin` md5 `0e5c05ee`): `PHook_AirEnter` at `$0107AC` is
`bsr.b $10818 / bset #3,$1E(a0) / rts`, and `PHook_EnsureStanding` at `$010818` ends
`swap d2 / sub.l d2,6(a0)`. `Player_Chardef` is `$EC5A` in this build. The recipe note's
`$EC4E` was from an older one.

**The controller's premise, tested.** It said that after CHAR-4 only the release frame still
ends with the head embedded (7 px deep), because the lift runs after `Glide_Collide` in that
frame, and that the first GLIDEFALL update then ejects it. **Confirmed.** The committed witness
run on the base ROM (`.runlogs/witness-orig-on-base.log`, exit 0) shows the release update
ending at y 523.875 with the head at -7. The next update's move puts the head at -6, and
`Air_CeilingBump` ejects it to 0 (y 530.250). After that the head is never embedded again.

## 2. Enumeration

### 2a. Every writer of `PSTATE_GLIDEFALL`

I grepped every `*.emp` for `PSTATE_GLIDEFALL`. Apart from the declaration, the state tables
and `Player_Animate`'s classifier, there are exactly four writers. All four are mid-air, and
all four leave the ability box:

| site | from | box before | S3K twin (y_pos written?) |
|---|---|---|---|
| `PState_Glide` `.release` | GLIDE, airborne | ability 21x21 | :30730, no |
| `Slide_Terrain` `.ledge_drop` | SLIDE, feet over a drop of 14 px or more | ability | :31031, no |
| `Knuckles_Gliding_WallCatch` `.fall` | GLIDE, after a wall hit | ability | :30893, no |
| `Climb_LetGo` | CLIMB, attached to the wall | ability | :31461, no |

I read the four S3K sites firsthand at those lines. Each one is `move.b default_y_radius(a0),

**Verdict: all four change.** They now enter through `PHook_GlideFallEnter`.

`Ground_DetachState`), and the insta-shield goes to JUMP. So the only mid-air ball-to-standing
lift is none at all. Sonic and Tails never reach GLIDEFALL: their `cd_ability` cannot enter
any ability state. For them the change is dead ROM, and the replay fixtures, which fold RAM
values, are unaffected.

### 2c. A fifth ability-box restore path, outside the brief's four: springs

`Touch_Spring` (engine `collision.emp`) seats the player on the spring face using his CURRENT
box. It then calls `Game.spring_launched`, and `Spring_Launched` (`games/sonic4/objects/
test_solid.emp`) enters AIR when he is not curled. If Knuckles is touched while in an
ability-box state, the box is the ability box, so `PHook_AirEnter` -> `EnsureStanding` lifts
9 px. GLIDE is the mid-air case.

That reachability is read from the box logic only. I did not trace whether the touch pass and
the spring's face geometry admit each of SLIDE, CLIMB and LEDGE, and I did not drive it at
runtime.

**I left it unchanged, and I am flagging it for a ruling rather than folding it in.** The lift
there is what keeps the spring seat. The seat was computed from the ability box's bottom edge,
and the feet-planted lift keeps the feet on it. A centre restore would put the feet 9 px inside
the spring object on the launch frame. The CHAR-4 up-class ceiling probe then covers the head
on the next frame, because a vertical spring launches upward.

On S3K's side, as far as I read: the up-spring handler `sub_22F98` (:47717) writes y_vel,
status, anim and routine, and no radius. In S3K a gliding Knuckles meets a solid object's top
through `RideObject_SetRide` -> `Knux_TouchFloor`, which restores the radii before any spring
code runs. I did not trace that far enough to state S3K's net y for a spring hit mid-glide.
**UNVERIFIED; this needs its own look.**

## 3. The design shipped (S3K-faithful default; no deviation)

`PState_EnterHooks.GlideFall` -> `PHook_GlideFallEnter`, a new same-module proc that is **not
`pub`**:

```
proc PHook_GlideFallEnter (a0: *Sst) clobbers(a1) {
        bclr    #ST_ROLLING, status(a0)
        movea.l Player_Chardef, a1
        set_standing_size(a0, a1)               // y_pos untouched: the centre is kept
        bset    #ST_IN_AIR, status(a0)
        rts
}
```

The box grows about its centre. The head rises Δr and the feet drop Δr, where
Δr = (cd_stand_h >> 1) - (ability h >> 1) = 19 - 10 = 9. Every grounded lift is unchanged.

### 3a. The next-frame corrections, proven from source

`PState_GlideFall` runs `ObjectMove`, then `Air_XInput`, then gravity (y_vel += $38, capped),
then `Glide_Collide`.

- **The feet.** `Glide_Collide`'s floor branch starts `tst.w y_vel(a0) / bmi .airborne` and
  then calls `Collision_ProbeDown` at (x, y + (h >> 1)) with `SOLID_TOP`. **It is not
  class-gated.** Only y_vel's sign gates it, and y_vel is at least $38 there: every entry
  starts with y_vel >= 0, and gravity is added before the call.
  - The four entries' y_vel on arrival:
    - glide release: at least 0, because the glide entry clamps it and the parachute never
      takes it below 0;
    - wall-catch fail: at least 0, as the glide's;
    - slide ledge-drop: 0;
    - let-go: 0, because the climb zeroes it every frame.
  - An embedded foot (dist < 0) is snapped by `y += dist`. The fall then dead-stops into
    GROUND, where `EnsureStanding` takes `.keep`.
  - The embed is bounded by Δr = 9. The glide feet had dist >= 0, or the glide would have
    landed instead of releasing. For the ledge drop the pair read >= 14, so the standing feet
    read >= 5 and are never embedded.
  - **Caveat (CHAR-5).** This is ONE centre sensor where S3K's is the pair (`sub_11FD6` ->
    `Sonic_CheckFloor`). A floor under a foot but not under the centre, such as a lip within
    9 px of x, is not caught. The foot then passes through the lip until the centre-height
    wall probe meets its side. That is CHAR-5's existing single-sensor divergence, and it
    applies to every GLIDEFALL frame. The centre restore starts it up to 9 px deeper than the
    feet-planted lift did.
- **The head.** CHAR-4's `Air_CeilingBump` runs in every class but mostly-down (|x_vel| <=
  y_vel with y_vel >= 0).
  - The embed is at most Δr = 9 when the glide head was clear before the release. That holds
    whenever the release frame was in a probing class, because CHAR-4 then left it clear. The
    old lift's bound was 18.
  - **Can mostly-down happen on the first GLIDEFALL update? Yes.** §6 (i) of the recipe note
    argues something narrower: a glide is nearly always horizontal, and when it is not, it is
    moving down, away from ceilings. It does not argue that a release cannot be mostly-down.
    From source:
    - wall-catch fail: its first fall update is always mostly-down. `Air_WallProbe*` zeroed
      x_vel on the hit, and `Air_XInput` adds at most one air-accel step (Knuckles' row) while
      y_vel is at least $38;
    - let-go: always mostly-down (x_vel 0, y_vel $38);
    - glide release: mostly-down when x_vel / 4 <= y_vel + $38. That happens near the vertical
      point of a turn, or early after an entry from a fast fall;
    - slide ledge-drop: only when the slide is slower than $38.
  - In those cases the head's up-to-9 px embed is not ejected. It leaves only as the fall
    carries it down. S3K has the same exposure: its mostly-down class has no ceiling probe
    (:32648-32678).
  - For the let-go, the climb-up path probes the ceiling at y - 18 every step, so after any
    upward climb the standing head (y - 19) starts at most 1 px deep. Idle and downward climbs
    probe nothing.

### 3b. The open call: no frame embedded? Declined, with the comparison

The baseline is the S3K-faithful hook: 92 cycles, 24 bytes, one frame with the feet in a floor
when one lay within 9 px under the glide's feet, and the landing snap on the next frame.

The alternative I costed would make the hook also probe the floor after the restore and snap
the feet out at once, so no frame ends embedded.

- **Cost.** `Player_SensorFloor` clobbers d0-d7/a1-a2, which is outside the PlayerHook
  contract (`clobbers(d1-d2, a1-a2) preserves(a0)`, with d0/d7 preserved by convention). So
  the hook would need a save/restore around the probe, plus the probe itself and a quadrant
  clear. That is several hundred cycles on the entry frame instead of 92, and roughly 20-30
  more bytes.
- **What it buys.** The landing pop (up to 9 px) moves one frame earlier. Nothing else
  changes. The sprite is drawn about y_pos, so under the centre restore it does not move on
  the release frame at all, where the old lift jumped it 9 px up. A snap-on-entry reintroduces
  a pop on the release frame whenever a floor is near.
- **It also has a hazard.** Snapping the feet up can push the head into a ceiling in the
  mostly-down classes, which have no ceiling probe.

**Not measurably better, so not taken.** The S3K form is also the cheapest.

### 4c. The witness (`tools/glide_ceiling_witness.py`)

**What changed.** Leg B was INFORMATIONAL and is now ASSERTED, and leg C is new. The
expectations are derived from design-independent quantities (the release update's unlifted
end position is prev.y + cur.y_vel * 256 on any design). Δr is read from the running player's
box bytes. Each leg has a subject requirement and a flat-surface check, and there is a floor
model control. The commit bodies (`4eb8977d`, `e423fd6d`, `dbf39bc5`) give the full account.

**Derivation of leg B's expectation.** At the release column x = 936:

- glide head clearance: +11;
- centre kept: 11 - Δr = **+2**;
- feet-planted lift: 11 - 2Δr = -7.

So the leg discriminates between the two designs. Leg B expects release excess 0, head +2, and
0 embedded updates.

**Derivation of leg C's expectation.** The floor's top row is 576, probed from the model. The
glide is released at y 562 with its feet 4 px above the floor. The standing feet then sit at
4 - Δr = **-5**. The next update must dead-stop them at 0.

## 5. Open items

1. **Springs (§2c).** A vertical spring hitting Knuckles in GLIDE, SLIDE, CLIMB or LEDGE
   restores the standing box through AIR with the 9 px feet-planted lift. This is a fifth
   ability-box restore path, unchanged here, and S3K's net behaviour is unverified.
2. **CHAR-5 interacts.** The next-frame feet correction is a centre sensor, so a floor under
   only a foot is not caught. Restoring S3K's pair in `Glide_Collide` (CHAR-5) would make the
   correction complete.
3. **The mostly-down first frames.** The wall-catch fail and the let-go always have them, and
   there the head's up-to-9 px embed is not ejected. This matches S3K.
4. **The grounded ability-box lifts** (glide slope landing, `Climb_ReachFloor`) remain the
   separately booked §6 (iii) divergence.
5. **Side finding.** `tools/measure_character_boxes.py`'s `STATE_BOX` lists the `GlideFall`
   animation state as the ability box. GLIDEFALL has run at the standing box since before this
   parcel. The row is marked not-grounded, so it produces no reading. It is left alone here.
