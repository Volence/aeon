## Verdict

**HOLDS.** The lost decode frame is real, but **the fix the sweep proposed is wrong**. Raising
the flag before the enqueue turns a benign, self-healing lost frame into silent tile corruption
of a published page that persists, and its race window is the same size. The branch does
something else: it keeps the current order and, right after the raise, re-tests the release
predicate that `VInt_Level` already uses ("Important queue empty") once. That is 14 bytes of
code in `PageIn_Process`'s `.land`, with no new flag, no change to `vblank.emp` code, and no
critical section.

### What `PageIn_EnqueueLanding` hands off to: the Important DMA queue

- **Enqueue.** `QueueDMA_Important` jumps to `QueueDMA_Deferrable.transfer`, whose whole body
  runs under `move.w #$2700, sr`. The callers are exactly `PageIn_EnqueueLanding` (the raw arm
  and `.land`) and `Perform_DPLC` (`perform_dplc(QueueDMA_Important)`). The callers of
  `Perform_DPLC` are object code: `characters.emp`, `tails_appendage.emp`, `test_animated.emp`
  and `test_player.emp`. **No Important enqueue runs in interrupt context.** This was checked by
  call site; `vblank.emp`'s straddle-instrument comment (point 1) says the same thing
  independently. Nothing else writes `DMA_Important_Slot` except `Init_DMA_Queue` (boot only)
  and the drain.
- **Drain.** `Process_DMA_Important`, reached ONLY from `VInt_Level`
  (`requires(vblank)`), tail-calls `Drain_Budgeted_Queue`. That sends entries from the base in
  order, stops at the first entry that does not fit `DMA_Budget_Remaining`, and compacts the
  survivors down to the base. **The drain always sends a FIFO prefix**, so "slot == base" means
  every entry that was queued has been sent. A 68k-source DMA halts the CPU until it completes,
  so "sent" means "landed". That is the same assumption the existing release (W2) relies on.
- **Also read in VBlank:** the DEBUG peak instrument reads `DMA_Important_Slot`. It does not
  matter here.

## 2. The interleaving that loses a frame (current order)

The code, `PageIn_Process` `.land` at cd075f2d:

```
391  jbsr  PageIn_EnqueueLanding   // Important staging->VRAM DMA; carry = dropped
392  bcs   .land_full
393  st.b  PageIn_Staging_Busy
```

1. A decode completes (`.after`, then `.land`), or the `Land_Pending` retry re-enters `.land`.
   `VBlank_Ready = 1`, because `VSync_Wait` set it before calling `PageIn_Process` and no VBlank
   has run since.
2. `QueueDMA_Important` enqueues the landing under `$2700`. The staging page is now the queue's
   LAST entry, since nothing else is enqueued between here and line 393.
3. **IRQ6 is taken anywhere between the core's `move.w (sp)+, sr` and line 393.** A VBlank that
   is asserted while the core is masked also counts: it is pending and is taken at the restore.
   `VBlank_Ready = 1`, so the handler runs `VInt_Level`:
   - `Process_DMA_Important` sends the queue. When the landing fits the window budget (which
     at init, with `DMA_BUDGET_BLANKED_INIT`, is every time) the queue ends at base.
   - The release test reads `PageIn_Staging_Busy == 0`, because it has not been raised yet, and
     takes `.staging_idle`. **The release is skipped.**
   - `VBlank_Flag = 1`, and `VBlank_Ready` is cleared. The PC is not in `ZX0R_Decompress`, so
     there is no bookmark.
4. The main loop resumes at 393 and raises `Staging_Busy` over a page that has already landed
   and an empty queue, then calls `Publish`. `VSync_Wait`'s `.wait` falls straight through,
   because the flag is already set.
5. The next frame's `PageIn_Process` reads `Staging_Busy != 0` at R1 and takes `.idle`. That
   frame gets **no decode start and no `PageCache_Prefetch` pass**. The following
   `VInt_Level` finds the queue empty (or empties it) and releases the flag, and the decode
   starts one frame late.

The loss is one decode start deferred by one frame per occurrence, plus the prefetch pass that
frame skips. There is no corruption: the flag is only ever set late, never cleared early. It is
self-healing. **The observable fingerprint at a main-loop instant is `PageIn_Staging_Busy != 0`
while `DMA_Important_Slot == DMA_Important`.** Only this race produces it; see the invariant in
section 4.

**Window size, DERIVED from 68000 timings and not measured.** After the restore:
`andi #,ccr` 20 + `rts` 16 + `movem.l (sp)+,d3-d4` 28 + `bcs` (not taken) 8 + `move.w` 12 +
`sub.w` to memory 16 + `andi #,ccr` 20 + `rts` 16 + `bcs` (not taken) 8 = **144 cycles**. Add the
masked core itself (on the order of 300 cycles on the no-split path), during which an asserted
VBlank pends. The total is on the order of **450 cycles per landing**. The seat's "rare, not
unreachable" framing stands. I have not measured a rate, and any per-landing probability would
rest on an unmeasured distribution of completion times, so none is quoted.

**Sub-case where it cannot fire.** If a VBlank already ran earlier in the same `PageIn_Process`
call (the documented resume-setup straddle), `VBlank_Ready` is 0 at `.land`. A second VBlank in
the window then dispatches `VInt_Lag`, which touches neither the flag nor the Important queue.

## 3. The proposed fix introduces a worse hazard

The sweep said: "Raise the flag before the enqueue and drop it on the carry (dropped) path." The
packet says "the seat proved the inverse unreachable". That is true, but **only for the current
order**, and the reorder is exactly what reopens it:

1. `st.b PageIn_Staging_Busy`, then `jbsr PageIn_EnqueueLanding`.
2. IRQ6 is taken between the raise and the core's `move.w #$2700, sr`. That span is the
   landing's art-budget check, `movem.l d3-d4,-(sp)`, two loads, `bsr`, `lea`, `move`, `bra`
   and the SR save, **on the order of 150 cycles**. `VBlank_Ready = 1`, so `VInt_Level` runs:
   the drain sends the earlier DPLC entries and the queue ends at base. The release test reads
   `Staging_Busy != 0` and `slot == base`, so it **releases**.
3. The main loop enqueues the landing, which is now the only entry, carry clear, and
   `Publish` marks the page resident in its frame. **`Staging_Busy == 0` while the landing
   is still queued.**
4. The VBlank set `VBlank_Flag`, so `VSync_Wait` returns at once. If the next logic frame
   finishes before the next VBlank (the normal, non-lagging case), `PageIn_Process` reads
   R1 == 0, dequeues and starts a ZX0 decode into `Art_Staging_Buffer`. **That buffer is the
   queued landing's DMA source.**
5. At the next `VInt_Level` the landing DMAs a buffer whose head now holds the new page's
   bytes, into the OLD page's frame. That page is already published and referenced by the
   nametable. **Wrong tiles on screen until that frame is evicted and reloaded, and for a
   `pm_flags`-pinned page, for the rest of the act.** No check in the tree sees it: V-7 nets
   1, 2 and 4 grade the decode, not the landing's source.

The carry-path rollback ("drop it on the carry path") is harmless in itself. The hazard is
entirely in step 2. **Do not land the sweep's fix.**

## 4. The fix on this branch, and why it is sound

```
    jbsr  PageIn_EnqueueLanding
    bcs   .land_full
    st.b  PageIn_Staging_Busy
    move.w DMA_Important_Slot, d0
    cmpi.w #DMA_Important, d0        // VInt_Level's own release predicate, same spelling
    bne   .landing_queued
    clr.b PageIn_Staging_Busy        // a VBlank already sent the landing
.landing_queued:
    ... Publish (unchanged)
```

Premises, each checked above:

- **P1.** Only main-loop code enqueues Important (section 1, by call site), and nothing
  main-loop runs between the enqueue and the re-test. So at the re-test the landing is the
  queue's last-enqueued entry.
- **P2.** The drain sends a FIFO prefix (`Drain_Budgeted_Queue`). So "slot == base" at the
  re-test means the landing has been sent. "slot != base" means it is still queued: anything
  left over sits at or before the landing, and nothing sits after it (P1).
- **P3.** Each read of `DMA_Important_Slot` is one word read, so no instruction can see a torn
  slot. The enqueue writes the slot under `$2700` in any case.
- **P4.** The only other writer of the flag is W2 (the release), and it applies the same
  predicate.

Every interleaving:

| IRQ6 (VInt_Level) lands | effect | end state |
|---|---|---|
| between the enqueue restore and the raise | landing sent, W2 skipped (flag 0) | raise, then re-test sees base, then clear. **Frame recovered.** |
| between the raise and the re-test | W2 releases iff the queue is empty, i.e. iff the landing was sent | re-test agrees: clear (idempotent), or leave it |
| between the re-test (base) and the clear | W2 sees flag 1 and base, clears | our clear repeats it |
| after the re-test saw not-base | nothing to reconcile | flag 1 while the landing is queued, and W2 releases it later |
| `Ready = 0` (`VInt_Lag`) anywhere | touches neither | as if no IRQ |

**Safety (the hazard section 3 would open).** The flag is cleared only on observing base, and
observing base means the landing has been sent (P2), so no staging overwrite under a queued
landing is reachable.

**Invariant, and the TAG below uses it.** At every main-loop instant outside `.land`,
`PageIn_Staging_Busy != 0` implies `DMA_Important_Slot != DMA_Important`. The only way to empty
the queue is the drain, and W2 follows it in the same handler. Before the fix, the race in
section 2 is exactly the violation.

**The cost of the coupling.** The release predicate now has two spellings: W2, and this re-test.
Both carry comments that point at the other (a line-neutral comment edit in `vblank.emp`'s
release block). Changing the release rule means changing both.

### Alternatives rejected

- **The sweep's reorder.** Unsafe, see section 3.
- **Bracketing enqueue and raise under `with ints_off`.** That closes both windows, but
  `PageIn_EnqueueLanding` returns its verdict in carry and the bracket's `move.w (sp)+, sr`
  restore overwrites CCR (`engine/irq.emp`: "any bracket with a CCR out-contract can NEVER
  adopt"). The verdict would have to be moved out through a byte (`scs PageIn_Land_Pending`),
  restructuring `.land`. It also extends the IPL-7 span, which masks HInt raster fires,
  across the landing's budget check, `movem` pair and budget charge. That is roughly 170 more
  masked cycles on top of the core's own span. The span is paid only per landing, but it adds
  raster jitter for no gain over the re-test.
- **Moving the raise into the DMA core, or changing the release in `vblank.emp`.** These are
  cross-module design changes and out of scope (brief rule 5). Neither is needed.

### V-7 interaction (the release-shape nets in `page_in.emp`, `d6ba4d60`)

- Net 1 (`.fault_ver`) and net 2 (`.fault_size`) sit on the ZX0 setup arm, before the decoder.
- Net 3 (`.fault_bank`) is in `PageIn_BankRegs`.
- Net 4 (`.fault_extent`) sits in `.after`, before the `.land` label.

All four branch to `raise_error` and never return. The `Land_Pending` retry reaches `.land`
without passing any of them. The new instructions sit strictly between the enqueue and
`Publish`, with no fault path in or out, and `d0` is inside `PageIn_Process`'s
`clobbers(d0-d2/a0-a3)`. Nothing new is pushed, so the stack-depth rule for the decoder
fall-through is untouched. `.land` is not on that path.

## 6. TAG: runtime confirmation (the controller's, needs an emulator)

**TAG, unverified at runtime.** Everything in this section is a prediction derived from source.
The controller confirms it at an emulator. This lane did not.

**What to watch.** Three symbols: `PageIn_Staging_Busy` (u8), `DMA_Important_Slot` (u16), and
the queue base `DMA_Important`, which is an address. Read all three out of the `.lst` of the
ROM under test, never from this note.

**The invariant (section 4).** At `PageIn_Process` entry,
`PageIn_Staging_Busy != 0` must imply `DMA_Important_Slot != DMA_Important`.

- "Lost frame" (pre-fix): a `PageIn_Process` entry where Busy is `$FF` and the slot is at
  base. That call then returns through `.idle` without dequeuing anything.
- "Fixed": no entry ever shows that pair.

A breakpoint on `PageIn_Process` that reads both cells on every hit checks this. Left to chance
the race is rare (window ~450 cycles per landing, section 2), so an unforced soak that shows no
violation is **not** evidence either way.

**Forcing it (a throwaway probe build, never landed).** Insert a VBlank wait in `.land` between
`bcs .land_full` and `st.b PageIn_Staging_Busy`:

```
    .probe_spin:
        tst.b   VBlank_Flag
        beq     .probe_spin
```

`VSync_Wait` clears `VBlank_Flag` before it calls `PageIn_Process`, and `VBlank_Ready = 1`, so
this forces a `VInt_Level` into exactly the section 2 window. Put the same three lines at the
same place (before the raise and re-test) in a probe of this branch.

- **Discriminator.** Read `Frame_Counter` at `Level_LoadArt`'s
  `clr.b PageIn_Bulk_Drain` (the end of the init bulk drain; display off, deterministic input).
  - Pre-fix probe: every ZX0-form page's landing is sent by the forced VBlank. The raised
    budget `DMA_BUDGET_BLANKED_INIT` lets it drain in that one VBlank, and the flag is then
    stranded for one frame. The drain should end about **one frame later per ZX0-form page**
    than in the post-fix probe.
  - Post-fix probe: at the invariant breakpoint, zero violations.
- **Control.** Build the two probes from one tree that differs ONLY in the fix, and confirm
  both boot the same act. Do not treat the expected frame difference as a number to
  hit exactly: it is a prediction, and the rarer sub-case in section 2 (`Ready = 0` at `.land`)
  can remove the forcing for an individual page.
- **Optional, for the rejected fix.** A probe of the sweep's reorder with the spin between
  the raise and the enqueue should show `Busy == 0` while the slot is past base at the next
  `PageIn_Process` entry, and then a decode starting under a queued landing: wrong tiles in
  the landed frame. That confirms section 3. It is not needed to land this branch.

## 7. What in the brief or the record was wrong

1. **The proposed fix is unsafe** (section 3). The sift row, the brief, and the packet's
   "Fix is an ordering with a rollback on the full arm" all prescribe it. The packet's own
   "the seat proved the inverse unreachable" is correct, but only for the order that is
   there now, and the reorder is what makes the inverse reachable.
2. **"The smallest reorder" does not exist.** Of the two positions available, one loses a
