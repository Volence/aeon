# `ojz_act_pool len must be shape-invariant` — adjudicated 2026-08-13

**Verdict: STALE PORT FIXTURE, not a shape-dependent leak into level data.**
The gate was corrected (sigil `0b818d4f`); nothing was re-baselined.

The 2026-08-13 Effects P2 handoff flagged this as the one merge blocker that had to be
investigated before touching, on the grounds that `debug_len == plain_len` for a ported
level section is the same invariant that killed the knuckles-c4 DEBUG test platform.
It is the same invariant — but this test was not measuring it.

## The numbers in the handoff were stale

The handoff recorded **"12056 vs 15166, a 3110-byte difference"**. At the repin tip
(sigil `a5b2a5b2`) the real values are:

```
pins.rs  OJZ_ACT_POOL  plain_len: 0x2F16 (12054)   debug_len: 0x2F18 (12056)
```

A **2-byte** delta, not 3110. The `15166` figure never corresponded to a committed pin
state; only `12056` (the debug length) survives into the tip. Anyone re-checking this
should take the numbers from the assert, not from the handoff.

## What the region pin actually measures

`sigil-harness/repin.toml` declares these regions **`end-is-next-placement`**:

```toml
[[region]]
name = "ojz_act_pool"
start = "OJZ_Act_Pool_Page0"
end   = "OJZ_Act1_Descriptor"     # <- the NEXT section's head label
```

So the pin's "length" is the distance to the **next section's start**, which includes
whatever inter-section fill the placer happened to leave. That is not the module's own
byte length, and it is shape-varying by nature:

- **50 of the 95 region pins already carry `debug_len != plain_len` on master**,
  including level data: `act_descriptor` +6, `sec_block_blobs` -12, `sec_local_maps` -14,
  `ojz_bg_anim` -12, `objdefs` -4.
- `act_descriptor` is this region's **immediate neighbour**, uses the identical
  `end-is-next-placement` pattern, has carried +6 since before this parcel, and its own
  port test never asserted equality.

`ojz_run_a_port` was the only test asserting a property the pin scheme explicitly does
not provide. It held for 100+ parcels by luck of placement.

## Evidence that the section itself is shape-identical

1. **Structurally incapable of shape variance.** `ojz_act_pool.emp` is generated by
   `tools/regenerate-level.sh`, contains zero `#if`/DEBUG conditionals, and the port test
   lowers it with `defines: vec![]` — **one compile is compared against both ROMs**.
2. **Byte proof.** Comparing `s4.bin[0x128A8 .. +0x2F16]` against
   `s4.debug.bin[0x130F8 .. +0x2F16]`:
   - the `0x2EC6` of ZX0 page embeds are **literally identical**;
   - exactly **20 bytes differ, in 10 two-byte runs**, one per `PageManifest.pm_source`
     Abs32 cell, each differing by **exactly the base delta `0x850`** — i.e. pure
     relocation, which is what a shape shift is supposed to look like.
3. **The 2 extra bytes are outside the section.** `0x1600E..0x16010` in the debug ROM is
   `00 00` — map fill (`fill = 0x00` in `games/sonic4/map.toml`) — sitting between the
   10th manifest record and `OJZ_Act1_Descriptor`. The page table is 10 x 8 = `0x50`
   bytes in both shapes.

Per-page spans are identical in both shapes (`0x49E, 0x4DE, 0x506, 0x538, 0x470, 0x43A,
0x4BC, 0x544, 0x5B8, 0x2AA`), as is `Page9 -> PageTable`. Only the trailing gap differs.

## The fix — sharper, not weaker

The equality assert was replaced by two checks that measure the invariant that is
actually load-bearing (*the module emits the same bytes in both shapes*):

1. **The existing byte comparison**, run from ONE compile against BOTH ROMs. This is the
   check that would have caught knuckles-c4: those 48 extra bytes were appended to sec0's
   object list, i.e. **mid-region**, so every later byte shifts and the compare diffs on
   the first one.
2. **A new tail check**: everything between the module's last byte and the next section's
   start must be map fill. Emitted data is not fill, so a debug-only record **appended to
   the tail** — the one case the byte compare would miss — is caught here.
3. Plus a guard that the next section never starts *inside* this one (that would mean the
   content really did shrink by shape, which is a real leak; the message says so).

**Negative-probed**, so the new check is known to be live and not vacuous: flipping
`MAP_FILL` to `0xFF` fails `ojz_run_a_debug_regions_match_reference` at exactly
`0x1600E`, naming the 2-byte gap.

## The lesson worth keeping

`end-is-next-placement` region lengths measure **the placer**, not the data. Never assert
two of them equal across shapes. If a future parcel wants an exact per-section length
gate, give the module a real end marker (`dust_anims` does this: `end =
"Ani_DustSpindash_End"`) rather than asserting on a next-placement span — but note that
adding a symbol perturbs the deb2 appendix and therefore the ROM, so it costs a full
re-freeze.
