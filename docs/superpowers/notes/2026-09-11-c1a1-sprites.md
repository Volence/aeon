# C1a-1 / CTRL-7: `Draw_Sprite` band-slot arithmetic, re-derived off the emitted bytes

**Date:** 2026-09-11. **Base:** `3492ce3a` (origin/master at dispatch). **Branch:**
`parcel/c1a1-sprite-band-count`. **Scope:** `engine/objects/sprites.emp` only. No emulator was
run; every cycle figure below is priced from the emitted instruction forms, not from the source.

## Verdict

**C1a-1 HOLDS, both halves.** The second `lea Sprite_Band_Counts, a1` in `Draw_Sprite` is
redundant, and `lsl.w #6` does one bit more work than `(band * 32 + count) * 2` needs.

**Measured saving: 14 cycles per registered object** (8 from the `lea`, 6 from the shift), and 6
bytes. The per-execution figure in the sweep (82 to 68) is exact against the emitted code.
**The per-frame figure is 924 only in the DEBUG shape.** The shipped release ceiling is **812**,
because the 8 System slots dispatch nothing in release (LS-10). The half the brief named (the
`lea` alone) is worth **8 cycles per object: 464 release / 528 DEBUG at the ceiling.**

| what is removed | cycles / exec | bytes | release ceiling (58) | DEBUG ceiling (66) |
|---|---|---|---|---|
| second `lea Sprite_Band_Counts, a1` | 8 | 4 | 464 | 528 |
| `lsl.w #6` stride, recast as `lsl.w #5` + doubling | 6 | 2 | 348 | 396 |
| **both (this branch)** | **14** | **6** | **812 (0.63%)** | **924 (0.72%)** |

Percentages against the sweep's own 128,010-cycle frame. These are CEILINGS: every occupied slot
on screen at once. The real per-frame count is a runtime fact this parcel cannot measure (no
emulator); see the TAG below for how to read it in one frame.

## 1. Is the reload really redundant? (source at `3492ce3a`)

`Draw_Sprite` (in `engine/objects/sprites.emp`) declares `clobbers(d0-d3/a1)`, no outputs, and
"Preserves: a0, d7". Walking a1 through every path:

- **Child-skip guard** writes a1 (`movea.w d0, a1`, the parent SST) and exits to `.offscreen`
  or falls to `.no_parent`. It never reaches the band code with that value.
- **`.no_parent`** writes a1 = `Sst.mappings`, then `adda.w Sst.frame_off(a0), a1` (frame data,
  bbox at +0). Null mappings exit to `.offscreen`. The X/Y culls read a1 and exit to `.offscreen`.
- **`.screen_coords`** (reached by the cull fall-through or by the `RF_COORDMODE` branch) then
  does `lea Sprite_Band_Counts, a1`. From here a1 = `Sprite_Band_Counts` on every path.
- **Entry 1 to `.band_has_room`:** `blo .band_has_room` straight after that `lea`. a1 unchanged.
- **Entry 2 to `.band_has_room`:** fall-through out of `.cascade`. The cascade loop body is
  `subq.w #1, d0` / `bmi .all_bands_full` / `move.b (a1,d0.w), d1` / `cmpi.b` / `bhs .cascade`:
  it READS a1 and never writes it. So a1 = `Sprite_Band_Counts` on this entry too.
- **Early exit `.all_bands_full`** (`bmi` in the cascade) is the `rts` AFTER both writes, so it
  performs neither; unchanged by the edit.
- **Inside `.band_has_room`** the ONLY write to a1 is `lea Sprite_Bands, a1`, used once by
  `move.w a0, (a1,d2.w)`. The second `lea` then restores the value the first `lea` had already
  established on both entries. a1 is dead after the increment (the next instruction is `rts`,
  and a1 is a declared clobber, not an output).

So moving `addq.b #1, (a1,d0.w)` to the top of `.band_has_room`, while a1 still holds the
counts, lets the second `lea` go. The pre-increment count the slot index needs is in d1, which
the increment does not touch (it writes memory).

**The reordering.** Before: store the SST word, then bump the count. After: bump, then store.
The two writes go to different arrays. Nothing between them reads either. The only code in
`engine/` or `games/` that names `Sprite_Bands` or `Sprite_Band_Counts` is `sprites.emp`
itself: `InitSpriteSystem` (clears the counts at frame start), `Draw_Sprite`, and
`Render_Sprites`, which runs in the game state's main loop after RunObjects (`children.emp`
says so, and every caller of Render_Sprites is a game-state proc). No `engine/system` IRQ code
references either symbol or `Draw_Sprite`, and no `tools/*.py` reads them. So no observer can
see the one-instruction window in which the count is ahead of the stored word.

**The shift half.** `band * 64 + count * 2 == (band * 32 + count) * 2` for all 16-bit values
(it is the same polynomial; the old form never overflowed, and neither does the new: band <= 7,
count <= 31, so the intermediate is <= 255 and the result <= 510). d1 is word-clean: `moveq #0,
d1` then `move.b`, and the cascade's `move.b` rewrites only the low byte, so `add.w d1, d2` adds
exactly the count. d0 is 0..7 and word-clean (`moveq` + `move.b` + `lsr.b #5`; the cascade's
`subq.w` exits on `bmi`). Both stay CODING_CONVENTIONS 2.5b-clean for the `(a1,d0.w)` index. d3
is no longer written; `clobbers(d0-d3/a1)` stays as declared (a caller may rely only on the
declared set; narrowing it is a contract change this parcel does not make).

The `#5` still hard-codes `SPRITES_PER_BAND == 32`, as the old `#6` did (and as
`Render_Sprites`' own `lsl.w #6` stride still does). No `ensure` pins it today; this parcel
neither adds nor removes that dependency.

**CTRL-7's own question (branch relaxation).** The C1a-1 saving is straight-line: there is no
branch on the `.band_has_room` path, so no relaxed form can move it. The branches that feed it
(`bcs.b` to `.band_has_room`, the cascade's `bmi.b`/`bcc.b`) are all SHORT in both shapes. The
edit also cannot flip a branch width in `Draw_Sprite`: the only two `.w` branches (see below)
target `.offscreen`, which moves 6 bytes CLOSER, and they stay out of short reach (displacements
$A6 to $A0 and $9C to $96, both still above $7F).

**What CTRL-7 predicted, found in this routine but outside this finding:** two of
`Draw_Sprite`'s entry branches ARE relaxed to `.w`: `bne .offscreen` after the multisprite-parent
`btst` (`$302E`, `660000a6`) and `beq .offscreen` on null mappings (`$3038`, `6700009c`). The
`.offscreen` tail is 166/156 bytes away. Not-taken, each costs **12 rather than 8**. The
null-mappings test runs on every call that is not a multisprite child, so that is **+4 cycles per
Draw_Sprite call** the source spelling does not show (the parent test adds +4 only for objects
with a parent). NOT FIXED HERE (it needs a layout change: a nearer exit, or moving the tail up);
recorded so it is not lost. At the 58/66 ceiling it is ~232/264 cycles per frame.

**C1a-3 (the other number CTRL-7 names), read the same way.** `perform_dplc`'s entry decode in
release `s4.bin` at `$2C94` (`$engine.objects.dplc$asm1$entry_loop`; `asm3` at `$2CE6` is the
second instantiation): `301a 3600 e04b e84b 5243` = `move.w (a2)+,d0` / `move.w d0,d3` /
`lsr.w #8,d3` / `lsr.w #4,d3` / `addq.w #1,d3`. `lsr.w #8` = 6 + 16 = 22, `lsr.w #4` = 6 + 8 =
14: **36**, as the seat said. The proposed `rol.w #4` (14) + `andi.w #$F,d3` (8) = **22**, so
14 per entry and +2 bytes, again exact against the emitted forms. The PER-FRAME half (~11
entries peak) is the seat's reading of the dplc module header and was NOT re-derived here: it is
a content count, not an emitted-form question.

## 3. How many times per frame

`.band_has_room` executes once per `Draw_Sprite` call that registers: the object has mappings,
is not a multisprite child, passes the four culls (or is screen-coord), and finds band room.
Band room cannot run out: capacity is `PRIORITY_BANDS * SPRITES_PER_BAND` = 8 * 32 = 256 against
at most 66 slots, and a full band cascades down rather than dropping.

`Draw_Sprite` is called from the tail of each object's routine (`jbra Draw_Sprite` in every
object under `games/`) once per frame per object, or, on a paused frame, from
`RunObjects_Frozen` once per occupied slot (RunObjects' paused path tail-branches there, so a
frame takes one or the other, not both). Slot population (`engine/system/constants.emp`):
`NUM_PLAYERS` 2 + `NUM_DYNAMIC` 40 + `NUM_SYSTEM` 8 + `NUM_EFFECTS` 16 = 66. In a RELEASE shape
the 8 System slots dispatch nothing (`engine/objects/core.emp` RunObjects, the LS-10 block: no
allocator, every writer is inside `if DEBUG == 1`, guarded by
`tools/test_system_pool_release_empty.py`), so the release ceiling is **58**; DEBUG is **66**.

**Content assumption:** the ceiling assumes every slot occupied, every occupant on screen, and
each calling `Draw_Sprite` exactly once per frame. No source path calls it twice for one slot in
a frame that this parcel found, but that was checked by call-site reading, not exhaustively. The
sweep's "~350 at a typical 25 objects" has no measurement behind it that the packet records;
the true per-frame count for the shipped OJZ act is what the TAG below reads.

## 6. TAG for the controller (emulator; this parcel ran none)

Behaviour should be identical: the same SST word lands in the same `Sprite_Bands` slot and the
same count results, only the order of the two RAM writes inside one main-loop call differs.
If you want to see it:

1. **Registration count (the real per-frame execution count).** At the end of RunObjects (before
   Render_Sprites) read the 8 bytes of `Sprite_Band_Counts` (release: from the listing, `$FFA684`
   at `3492ce3a`; the address may shift, look it up) and sum them. That sum IS the number of
   `.band_has_room` executions that frame; times 14 is this parcel's saving in cycles. A few
   frames of normal OJZ play would replace the ceiling in section 3 with a content figure.
2. **Equivalence.** With the same input replay on base and branch, `Sprite_Bands` (512 bytes)
   and `Sprite_Band_Counts` (8 bytes) should be byte-identical at the same frame, and the SAT
   buffer too. Any difference is a defect in this parcel.

## 7. What was wrong in the brief

- The brief's fix ("increment while a1 still holds it and drop the second `lea`") is only HALF
  of C1a-1. The ledger title and the packet name a second half, the one-bit-too-far `lsl.w #6`,
  and the 924 / 14-cycle figure is the SUM of both (8 + 6). A lea-only fix is worth 8 cycles and
  would have left the row half open. This branch does both, as two separate commits, so the
  controller can take either.
- 924 is the DEBUG-shape ceiling. The shipped release ceiling is 812 (58 slots, LS-10).
- CTRL-7 covers C1a-3 (154 c/frame) as well as C1a-1; the per-execution half of C1a-3 is settled
  above, its frequency is not.
- `s4.lst` has no instruction text; the forms come from disassembling the ROM at listing
  addresses.
