# B joins the jump mask — oracle A/B evidence

Evidence packet for the `b-jumps` provenance chain entry, per
`sigil/crates/sigil-harness/golden/ab/AB_PROTOCOL.md`. Class: **BA**
(behaviour-adjacent, player-facing input change). Follows `cheat-flag` (chain 43),
which freed B by moving debug-fly behind a runtime bit.

## The ruling

Classic Sonic jumps on **all three** face buttons — A, B and C are interchangeable
and it does not matter which one you mash. Aeon had `BUTTON_JUMP_MASK = BUTTON_A |
BUTTON_C` because B was carved out as the debug-fly toggle. Once `cheat-flag`
gated debug-fly, B did **nothing at all** in a release build: a player who
instinctively jumps with B got silence, and the deviation was the kind nobody can
name but everybody feels.

Owner ruling (Volence, 2026-08-05): **B jumps while `CHEAT_DEBUG_FLY` is clear;
while the bit is armed, B stays the debug-fly toggle and does not jump.** Default
players get the classic scheme; anyone who has deliberately enabled the cheat
accepts that B belongs to the cheat.

## The hazard that shaped it

The A/B conflict is on **exiting** debug-fly, not entering. Entering returns early
through `Player_DebugMove` and never reaches the jump code. Exiting clears
`debug_flag`, falls through to normal physics, and the jump latch would then see
that *same* B press and latch a jump as well — you would leave debug-fly and
involuntarily hop. Hence B must leave the mask exactly while the bit is armed,
which is what the ruling says.

## Two consumers that had to agree

1. `player_common.emp` — the jump-buffer **press** latch.
2. `player_air.emp` — the variable-jump-height **held** check (`PPHYS_RELEASE_CAP`).

If B latched a jump but did not sustain it, B-jumps would get a clipped arc: a
subtle feel bug, and a miserable one to trace back to an input mask. `BUTTON_JUMP_MASK`
was declared **twice**, once per file — that duplication *was* the drift hazard, so
it is now collapsed: `player_common` is the sole authority and exports
`BUTTON_JUMP_MASK` (`A|B|C`) plus `BUTTON_JUMP_MASK_NO_B` (`A|C`), and `player_air`
imports both.

The *gate logic* is deliberately NOT shared. The two consumers need opposite flag
polarity on the fall-through (`beq .no_latch` vs `bne .no_cap`), and any single-exit
form guaranteeing correct Z costs a scratch register plus ~16 cycles on the common
path. Sharing the data and not the control flow is the right seam.

## Cost

Mask `A|B|C` first, short-circuit, and probe the cheat byte only when a jump button
is actually present:

- **Press latch:** `d6` holds edge bits, so on the overwhelming majority of frames
  the first `andi`/`beq` exits in **18 cycles — identical to before**. The cheat
  probe runs only on a real jump-press frame.
- **Held check:** unchanged 18 cycles when no face button is held; +24 only while
  `AIRF_RELEASE_CAP` is set *and* rising past the cap *and* a jump button is held —
  a few frames per jump.

A branchless mask-build (`and`/`lsl`/`eori`) costs ~42 cycles *unconditionally* on
both paths, so it is strictly worse. Nothing is cached: both sites read the live
`Cheat_Flags` byte, so a future cheat code arming the bit mid-frame takes effect
immediately. `Player_Main`'s earlier `Cheat_Flags` load is unusable for this —
`Player_DebugExit` clobbers `d0-d2`, and the toggle's own branch skips that load
entirely when B is not pressed. `d0` is dead at both gate sites, so `d6`'s press-bit
contract and `d1`'s scratch role are untouched.

### The probe form, and why it is `moveq`/`and.b` rather than `btst`

The first cut used `btst #CHEAT_DEBUG_FLY_BIT, Cheat_Flags`, which clobbers no
register at all and is the obvious choice. **The strict suite rejected it**, and the
reason is worth recording: `games/sonic4/config/constants.emp` `pub const`s are
harvested into **link EquSyms**, so in a port test's standalone compile BOTH operands
of that `btst` are link-time symbols — `[lower.imm-link] a link-time immediate
combined with another symbolic operand is not yet supported`. The full build folded
it (same-compilation const) and was green, so **only `test_p2_player_states_port`
caught it**; `andi.b #BUTTON_JUMP_MASK, d1` was fine throughout because it has just
one symbolic operand.

The fix is the idiom the `cheat-flag` parcel already established and proved —
`moveq #CHEAT_DEBUG_FLY, d0` / `and.b Cheat_Flags, d0` — now used at all gate sites,
so there is exactly one way this engine tests a cheat bit. `CHEAT_DEBUG_FLY_BIT` and
its `ensure` are gone with the `btst` that needed them: a second spelling of the same
bit existed only to serve that instruction form.

## Emitted bytes — the gate is provably present

`Player_Main` press latch, `s4.bin` `$100CC`:

```
100CC  0206 0070        andi.b  #$70,d6        ; A|B|C  (was #$60 = A|C)
100D0  6716             beq.s   $100E8         ; no jump button -> .no_latch
100D2  7001             moveq   #1,d0          ; CHEAT_DEBUG_FLY
100D4  C038 B464        and.b   (Cheat_Flags).w,d0
100D8  6706             beq.s   $100E0         ; clear -> .latch (B jumps)
100DA  0206 0060        andi.b  #$60,d6        ; armed: strip B
100DE  6708             beq.s   $100E8         ; B-only -> .no_latch
100E0  11FC 0002 B477   move.b  #2,(Player_JumpBuffer).w
```

`PState_AirShared` release-cap held check, `s4.bin` `$1092A`:

```
1092A  1238 802C        move.b  (Ctrl_1_Held).w,d1
1092E  0201 0070        andi.b  #$70,d1        ; A|B|C
10932  670E             beq.s   $10942         ; nothing held -> .cut_arc
10934  7001             moveq   #1,d0          ; same gate, same idiom
10936  C038 B464        and.b   (Cheat_Flags).w,d0
1093A  670C             beq.s   $10948         ; clear -> .no_cap (B sustains)
1093C  0201 0060        andi.b  #$60,d1        ; armed: strip B
10940  6606             bne.s   $10948         ; -> .no_cap
10942  316C 000E 000C   move.w  $E(a4),$C(a0)  ; y_vel = PPHYS_RELEASE_CAP
```

Byte-for-byte the same shape at both sites, which is the point.

## Left alone deliberately

`TestPlayer_Main` jumps on **C only** and uses **A** as its free-flight turbo
modifier, with its own `btst #5`/`#6` literals. It ships in release and shares the
`CHEAT_DEBUG_FLY` gate for its B toggle, but it is scaffolding with a deliberately
different input map, so its jump was not touched. The broader "should `test_player`
ship at all" question is already an open item in `docs/DEFERRED_WORK.md`.

> **Harness finding, unrelated to this parcel but it cost real time:**
> `emulator_press` does **not** produce a fresh press edge when no emulated frames
> elapse between two calls. It releases the buttons but leaves the emulator paused,
> so the engine never sees the release in `Ctrl_1_Held` and computes no new edge —
> two back-to-back `press` calls read to the game as one continuous hold. Interpose
> a `resume`/`pause` (or a press of something else) between them. This made the
> first exit-toggle test look like a failure when the code was correct, and it will
> silently break any input-edge test that does not know about it.
