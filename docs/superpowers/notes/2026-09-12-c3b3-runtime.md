# C3b-3 runtime witness: the page-in race is real, and the fix recovers every forced frame (2026-09-12)

Controller run, emulator (Oracle, this session's own instance). Closes the **C3b-3 RUNTIME TAG** booked
with merge `b29a53ae` in `docs/DEFERRED_WORK.md`: the fix landed on analysis plus four green shapes and
was not runtime-witnessed. Method and prediction: `docs/superpowers/notes/2026-09-11-c3b3-pagein.md`.

## Subjects: three throwaway probe builds (never landed)

A worktree agent built them on branches `probe/c3b3-race-{unfixed,fixed,fixed-control}` (deleted after
this measurement). Every probe adds the same five lines in `PageIn_Process` `.land`, right after
`bcs .land_full`: a spin on `VBlank_Flag` (`tst.b VBlank_Flag` / `beq .probe_spin`, bytes `4a38 8000 67fa`,
followed by `50f8 ba4e`, `st.b PageIn_Staging_Busy`, read from the ROM bytes). `VSync_Wait` clears the
flag and sets `VBlank_Ready` before its only callee `PageIn_Process`, so the next VBlank is the full
`VInt_Level`: it sends the just-queued landing while the busy flag still reads 0. That is the race of
section 2, forced at every landing.

**The briefed pair was not a clean control, and the agent said so:** `origin/master` was 49 commits past
the fix, so the "fixed" probe differed from the unfixed one in far more than the fix. It built a third,
`fixed-control`, on `b29a53ae` itself; its diff against the unfixed probe is exactly the fix commit's four
files, with the same `PageIn_Process`, spin and `clr.b PageIn_Bulk_Drain` addresses. **The comparison
below is unfixed vs fixed-control.**

| probe | base | cksum | emulator-side CRC32 of the loaded cart |
|---|---|---|---|
| unfixed | `3492ce3a` (first parent of `b29a53ae`) | `3064938474 847387` | `0x22AEE8D3` (= the build's `crc=`) |
| fixed-control | `b29a53ae` | `4118751042 847409` | `0xE7060C57` (= the build's `crc=`) |

Each ROM was loaded with its OWN listing. RAM addresses from those listings: `PageIn_Staging_Busy`
`$FFFFBA4E`, `Frame_Counter` `$FFFF8002`.

## Method

Fresh load (reset), a record-mode write watchpoint on `PageIn_Staging_Busy` (a fresh handle per ROM, so
the logs cannot mix), `run_to $90C2` (`Level_LoadArt`'s `clr.b PageIn_Bulk_Drain`, the same address in
both probes), then read `Frame_Counter` and the flag's write log.

## Result

| | unfixed | fixed-control |
|---|---|---|
| emulator frame at `$90C2` | 62 | 52 |
| `Frame_Counter` at `$90C2` | `$3C` = 60 | `$32` = 50 |
| raises (`st.b` after the spin, `$9378`) | 10, at frames 35, 38, ... 61 (every 3) | 10, at frames 35, 37, ... 51, 52 (every 2) |
| who clears each raise | `VInt_Level` (`$2430`, the W2 release), the NEXT frame | the fix's re-test `clr.b` (`$9386`), the SAME frame, ~308 mclk after the raise |

**Ten forced races, ten frames recovered: one frame per forced page**, the fix note's prediction. What
would have falsified it, named before reading: fixed-control's clears coming from `VInt_Level` a frame
later, or both probes finishing on the same frame. Neither happened. In the unfixed probe the flag stays
set across a VBlank that has already emptied the queue, which is the section-4 invariant violation; in
fixed-control it never does.

## Scope, stated so it is not over-read

The spin forces the race at EVERY landing, so this measures the fix's recovery under a worst case the
shipped game hits only rarely; it does not measure how often the race fires unforced. One level load
(OJZ act 1, DEBUG shape). The invariant was read from the flag's write log (who clears, and when), not
from a breakpoint at every `PageIn_Process` entry.
