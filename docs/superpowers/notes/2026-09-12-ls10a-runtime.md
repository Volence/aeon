# LS-10a runtime witness: the release System pool stays empty (2026-09-12)

Controller run, emulator (Oracle, this session's own instance, bus `own-instance`). Closes the runtime
rider booked with LS-10 / C1b-1: the release shape no longer sweeps the 8 System slots, and until
now that was proven from source and shipped bytes only, never at runtime.

## Subject

- ROM: release `s4.bin` built by `tools/landing_build.sh` in the landing checkout at merge `ad707b83`
  (the lens-Z3 landing; master's bytes). cksum `453852737 821123`, md5 `0b93e768b265dc5c218d24f3967b8bdd`,
  CRC32 `0x52828985`. Copied to a stable path before loading; the emulator's own `memory_hash` over
  the whole cart window returned `0x52828985`, so the bytes running were the bytes on disk.
- Symbols: that build's `s4.lst`, bound `match`, 2527 symbols.
- Pool geometry read from that listing, not typed: `System_Slots` = `$FFFF9C90`, `Effect_Slots` =
  `$FFFF9F10`, `NUM_SYSTEM` = 8, so 640 bytes, 80 per slot (the emulator's decoded layout agrees:
  slots 42-49, `slotBytes` 80).

## Method

One write watchpoint (record mode, never breaking) on byte 0 of each System slot (w0-w7:
`$FF9C90 + n*$50`), plus a CONTROL on byte 0 of the top Dynamic slot (w8, `$FF9C40`), which the
dynamic allocator fills first. Armed at frame 0, then `emulator_reset` (watchpoints survive; all nine
listed at matched 0), then boot, then a scripted `play_input` run: right held 1500 frames with a
20-frame A jump every 90 frames. Whole-region `memory_hash` of the 640 bytes at the end.

## Why the first two attempts are NOT the evidence (kept because they would have read as passes)

1. Holding right from frame 400 for 900 frames: zero hits and an all-zero region, but Sonic had not
   moved (x 240; he stood against the red post), so nothing was exercised. `Ctrl_1_Held` read `$08`,
   so the input reached the game; the route was the problem.
2. A later control segment (left, 900 frames) left the Dynamic pool's hash unchanged
   (`0xCB7B98A6` before and after) and w8 unhit: no churn on that stretch, so the control could not
   discriminate. Zero hits there said nothing about the instrument.

The reset-with-watchpoints-armed run below is the one where the control fires on the same
addresses under test.

## Result (fresh boot, frame 0 to 1900)

| watch | address | hits | writers |
|---|---|---|---|
| w0-w7 (System slots 0-7) | `$FF9C90`..`$FF9EC0` | exactly 2 each | `EntryPoint.clear_ram` (frame 2, value 0), `InitObjectRAM.clear` (frame 25, value 0) |
| w8 CONTROL (top Dynamic slot) | `$FF9C40` | 5 | the same two clears, then `Load_Object`+14 (frame 25, `$2660`), `Spring_Init.red`+38 (frame 37, `$26BA`), and a gameplay write at frame 960 (PC `$2E6E`) |

- Sonic travelled x 240 to x 6120 during the play run (player_state), and the Dynamic pool's hash
  changed across an earlier identical route, so objects spawned and died on it.
- The 640 System bytes hash to CRC32 `0x4B7716DA` at frame 1900, which is the CRC32 of 640 zero bytes
  (computed locally with `zlib.crc32(bytes(640))`).
- Boot is deterministic: frame 400 reached identical mclk (358416030) on both boots.

**Verdict: no code writes the release System pool after object-RAM init, on this route.**

## Scope, stated so it is not over-read

One route, Sonic only, OJZ act 1, release shape, 1900 frames. The watchpoints cover byte 0 of each
slot (where every spawn writes its code pointer); the end-of-run hash covers all 640 bytes but cannot
see a write-then-clear inside the run on bytes other than byte 0. The standing static net remains
`tools/test_system_pool_release_empty.py`; this is a runtime witness beside it, not a replacement.
