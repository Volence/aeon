## 1. Two corrections to the brief, made before any number was taken

**(a) The quantise and dedupe stages are NOT in `tools/inject_editor_bg.py`.** That tool consumes
an already-quantised override JSON (`{"layout": [...], "tiles": [[64 px]...]}`) and emits
`bg_tiles.bin`. The PNG → tiles path — per-tile CRAM-line quantisation and flip-canonical dedupe —
is **`tools/png_to_bg_override.py`** (`quantise_tile` at `tools/png_to_bg_override.py:132`,
`flip_variants`/`canonical` at `:148`/`:152`). `inject_editor_bg.py` contains no PNG code at all
(`grep -n "png" tools/inject_editor_bg.py` returns nothing). The measurement therefore uses both
tools: `png_to_bg_override.py` for the count, `inject_editor_bg.py` for the header that reports it.

**(b) The waterline strips are 48 tiles, not 72.**
`games/sonic4/vram.toml:337-341` — `name = "waterline_strips"` … `base = 1400`, `tiles = 48`.
The `constants.emp` comment above the constant says 48 as well. Nothing in this tree declares 72.
The row-2 threshold in the brief ("just above capacity, up to ~448") still holds numerically,
because 376 + 48 = 424 and the physical run `$8000..$B7FF` is 448 slots — but the tiles that would
have to move are 48, and moving all of them only reaches 424, not 448.

**(c) Incidental, found while checking (b): `engine/system/constants.emp:655` carries a stale
trailing comment.** The line reads

```
pub const VRAM_WATERLINE_STRIPS = BG_TILE_BASE_VRAM + BG_TILE_CAPACITY * 32   // $B200 (slot 1424)
```

`$B200`/slot 1424 was the value when `BG_TILE_CAPACITY` was 400. At 376 the expression evaluates to
`$8000 + 376*32 = $AF00`, **slot 1400** — which is exactly what `games/sonic4/vram.toml:340`
declares (`base = 1400`). So the *declaration* is correct and consistent; only the comment is two
capacity moves behind. No behaviour is affected. **Not fixed here** (E3 is measurement-only);
flagged for whoever owns that file next.

## 2. What the 2-byte length header actually counts

**BYTES, not tiles.** `tools/inject_editor_bg.py:1358`:

```python
        f.write(struct.pack('>H', len(blob)))
```

`blob` is the packed 4bpp pixel data built immediately above (`tools/inject_editor_bg.py:1345-1351`:
eight rows × four bytes per tile = **32 bytes per tile**), and the docstring at
`tools/inject_editor_bg.py:7-8` says so in as many words — *"2-byte BE byte-length tile blob header"*.

**Conversion used throughout this note: `tiles = header_word / 32`.**
Worked on the shipped file as a sanity anchor:
`games/sonic4/data/generated/ojz/act1/bg_tiles.bin` is 10,242 B, header `0x2800` = 10,240,
10,240 / 32 = **320 tiles**, and 2 + 320×32 = 10,242 B closes the file size.

### What the dedupe actually does (read, not assumed)

- **Flip-canonical**: the key is `min()` over the four flip variants of the 8×8 index array
  (`canonical()` / `flip_variants()`); a tile and its mirror cost one tile and differ only in the
  nametable word's H/V bits.
- **Dedupe is on PIXEL INDICES ONLY.** The CRAM line is chosen per tile and stored in the
  *nametable word*, not in the key — so two tiles with the same index pattern on different palette
  lines share one blob tile. This matters for the union question: cross-picture sharing does not
  require the two pictures to use the same palette line.
- **Opaque**: index 0 is excluded from the quantiser's candidate set (`opaque=True`, `d[:, 0] = inf`),
  so no tile can quantise to transparent. There is **no blank-tile special case** — a flat tile is
  an ordinary tile.
- **No palette splitting beyond line choice**: lock mode (the default) picks, per 8×8 tile, whichever
  of the candidate CRAM lines (default `2,3`) minimises squared error. Nothing is recoloured, nothing
  is stamped.

## 5. The union is a real union, and the zero saving is real — how that was established

The measurement script folds both pictures through **one** `key_to_local` dict and **one** `blob`
list: the second picture's canonical keys are looked up in the first picture's keys, and only
genuinely new keys are appended. It is not two independent runs added together.

`union == naive sum` is exactly the pattern the brief said to distrust, and the script's own guard
fired on it. Three checks, all run:

1. **Positive control — the same picture twice.** If the shared dict were not being consulted across
   images, this would give 640.
   ```
   $ python3 docs/superpowers/notes/2026-09-15-regions-p2-e3-measure.py --lines 2,3 <forest.png> <forest.png>
   single ojz_forest_flowers.png: 320 unique tiles (64x64 cells)
   single ojz_forest_flowers.png: 320 unique tiles (64x64 cells)
     after ojz_forest_flowers.png: union 320 (+320 new, 0 shared with earlier)
     after ojz_forest_flowers.png: union 320 (+0 new, 320 shared with earlier)
   union 320  naive sum 640  shared saving 320
   ```
   **Cross-image lookup is live.** The zero is a property of the two pictures, not of the harness.

2. **Direct set intersection**, computed independently of the interning code:
   `|forest_keys| = 320`, `|cave_keys| = 448`, `|forest_keys ∩ cave_keys| = 0`.

3. **Mechanism, so the zero is explained rather than merely observed.** The only realistic candidate
   for a shared 8×8 tile between two unrelated pictures is a *flat* tile, and the two pictures' flat
   tiles use different palette indices:
   ```
   forest flat tiles by index: {}            # the forest has NO flat tile at all
   cave   flat tiles by index: {9: 80}       # the cave's most common tile is flat index 9, x80
   ```
   With no flat tile in the forest and 64-nibble exact (up to flip) matching required, zero overlap
   is the expected outcome, not an anomaly. **Do not read this as "backgrounds never share tiles"** —
   it is a statement about *these two* pictures, which were authored independently. Two pictures
   drawn from a common tile vocabulary would share plenty.

## 6. Confound work: are 320 and 448 measurements, or artifacts?

**320 is suspicious on its face: it is exactly `BG_STATIC_TILE_BUDGET`.** Varying what would hold it
fixed:

| candidate CRAM lines | forest | cave | union |
|---|---|---|---|
| `2` | 320 | 448 | 768 |
| `3` | 320 | **420** | 740 |
| `1,2,3` | 320 | 448 | 768 |
| `2,3` (default) | 320 | 448 | 768 |

The cave moves (448 → 420) when the palette candidates change, which proves the pipeline is not
pinning either number to a constant. The forest does not move. So the forest was chased down to its
**picture-intrinsic** count, measured palette-free:

```
ojz_forest_flowers distinct RGB 22   flip-canonical RAW-COLOUR unique tiles 320
ojz_cave_lilypad   distinct RGB 42   flip-canonical RAW-COLOUR unique tiles 448
```

i.e. **320 and 448 are the counts of distinct flip-canonical 8×8 blocks in the source pictures
themselves, before any palette is applied.** Palette quantisation can only merge tiles, never split
them, so these are hard floors; for the forest at lines 2/3 nothing merges, so the floor is reached.

**Conclusion on the confound: 320 is a genuine measurement that also equals the budget, and the
equality is not a coincidence in the innocent direction — it is authorship.** `e192062e`'s own commit
message says the forest source is *"aurora's auto-simplified picture"*, simplified until it fit; it
printed `unique tiles: 320/320  (bg_region 448 - band_reserve 128)` at a moment when the budget was
*also* 320 by a different arithmetic. My run reproduces that commit's numbers exactly, including
`cells per CRAM line: line2=3804, line3=292`. **448 for the cave carries no such story** — its equality
with the *old* 448-slot capacity is pure coincidence, since 448 is the raw picture's intrinsic count.

### Documented bypasses, and why each is not a method degradation

Two independent **policy** gates refuse a >320 / >376 tile set, and both were bypassed *only* to
read a header, never to obtain a count:

- `check_tile_budget` (`tools/png_to_bg_override.py:156`) — not called by the measurement script;
  the count is taken at the same place the importer takes it, one line earlier.
- `assert len(tiles) <= BG_TILE_CAPACITY` (`tools/inject_editor_bg.py:1324`) — for the cave and union
  runs only, `inject_editor_bg.BG_TILE_CAPACITY` was rebound to 4096 in the driver, printing a loud
  `[BYPASS]` line each time. **The packing code is untouched**; the emitted blobs are the shipped
  format. Validation that this is faithful: the *forest* run was done with **no** bypass, and its
  header (`0x2800` = 320 tiles, 10,242 B) matches the shipped `bg_tiles.bin` byte-count exactly.

The union has no first-class representation in the pipeline — one override file describes one
picture — so the union override JSON was constructed by the measurement script from the tools' own
quantise/dedupe output. That is a genuine deviation from "run the shipped tool", stated here rather
than hidden.

## 7. The carried 320, and a stale doc

**Carried figure:** `docs/superpowers/designs/2026-09-03-vram-replan-item0-design.md:359` measured the
*shipped blob* at 320 tiles. **My re-derivation of the forest PNG also gives 320. They agree.**

But they are agreeing about **two different objects**, and that is worth recording:

- the **shipped** `editor_bg_override.json` has keys `['anims', 'layout', 'tiles']` and 320 tiles;
- a **fresh import** of `ojz_forest_flowers.png` also has 320 tiles;
- **they share only 199 of those 320 tiles** (order-free set comparison), and neither `layout` nor
  `tiles` is identical.

So the shipped background is *not* a byte-identical re-import of that PNG — a later writer
(`tools/forest_bg_gen.py`, which authors `anims`; `png_to_bg_override.py` refuses to write over that
key) rewrote `layout`/`tiles`, and its result also totals 320. **The three 320s — shipped blob, fresh
forest import, static budget — are three separate facts that happen to coincide.** Nothing here is
wrong, but "the forest is 320" should not be quoted as though one measurement established all three.

**Stale doc, confirmed:** `docs/ART_PIPELINE_CONTRACT.md` states `BG_TILE_CAPACITY = 400` at **lines
225, 233, 432 and 1544**. All four are wrong at `0dc0ff11`; the value is 376
(`engine/system/constants.emp:648`). On the specific open question about the **80-tile
`band_reserve`** at `:233`: **the name is alive, the value is stale.** `band_reserve` still exists
under exactly that name in `games/sonic4/vram.toml:228`, and `BG_BAND_RESERVE` still exists in
`tools/vram_map.py:36` — both at **56**, not 80. Not fixed here; E3 is measurement-only.

## 8. The decision row

| union tile count | consequence | lands? |
|---|---|---|
| ≤ 376 | two pictures coexist on one tile set | no |
| just above, up to ~448 (needs the waterline tiles to move) | coexists only at an owner look cost | no |
| **well above that** | **one picture, two anchors only; art variety waits for tile paging** | **YES** |

**How near the boundary: not near at all.** The union is **768**, which is **392 over capacity**
(2.04× the arena) and **320 over** even the optimistic ~448 physical-run ceiling. This is not a
"capacity minus 2" answer that a small art tweak could flip.

Two further facts that close off the obvious escape routes, so the owner does not have to ask:

- **The cave does not fit alone.** At 448 it is 72 over capacity and 128 over the static importer
  budget. Even *replacing* the forest with the cave is refused today without simplifying the art.
- **Spending every reserve does not help.** 376 capacity + 48 waterline = 424; the whole physical
  run `$8000..$B7FF` is 448 slots. The union needs 768. There is no carve of the current map that
  reaches it.

**Consequence for the showcase, in one sentence:** the first on-screen showcase cannot be a second
*picture* under the night region — it must be two anchors into the one existing background (or a
deliberately cheap, forest-vocabulary second layout authored to share tiles), because a genuinely
independent second picture needs roughly twice the BG arena that exists.

## 9. What I could NOT establish

- **Whether a *purpose-built* second picture could fit.** Everything here measures the two PNGs that
  exist. The zero saving is a fact about *these* two independently-authored images; art drawn against
  the forest's tile vocabulary could share a great deal. That is an art-pass question, and E3 did not
  attempt it.
- **What the cave would cost after simplification.** `e192062e` shows aurora can auto-simplify a
  picture to a tile target; nobody has run that on the cave. Unmeasured, not zero.
- **No runtime confirmation of anything.** No build, no ROM, no emulator — by design. Nothing in this
  note depends on a running binary, so there is nothing TAGGED for foreground emulator follow-up.
- **`docs/ART_PIPELINE_CONTRACT.md`'s other figures** beyond the capacity/reserve lines I was asked
  about were not audited.
